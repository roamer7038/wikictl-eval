## 結論

### 1. 情報がローカルにある場合（B1・B2）と、ない場合（B0）

- 事実: B0 の点は 0.23〜0.31 で、成功は Haiku の L1 と L2 の 1 回ずつだけ。B1・B2 系は Opus・Sonnet で 0.99〜1.00、Haiku で 0.84〜0.90。B0 は 2026 年に変わった値を古い値で答えた。
- 解釈: 対象の文書を読めるかどうかの差は大きく、モデルの知識では代えられない。

### 2. B2 が B1 と同等以上になるには何が要るか

- 事実（素の B2）:
  - 点は B1 と同じ水準だが、USD は 1.19〜1.80 倍、時間は 1.73〜2.31 倍。
  - wikictl のプロセスにかかった時間は、B2 の実時間（P9 を除く）の Opus で約 24%、Sonnet で約 20%、Haiku で約 66%。B1 との時間の差に対しては、Opus で約 5 割、Sonnet で約 4 割。
  - ファイルを 1 つずつ読む `cat` の繰り返しは Haiku で顕著だった（1 グループで P3K 496〜2,853 回、P3M 128〜1,485 回。Opus は 4〜7 回、Sonnet は 1〜129 回）。
  - `cat` 1 回の中央値は、fetch のある v0.4.1 で 364 ms、fetch を省いた試作で 66 ms。
  - 履歴を読む手段がなく、P4 で規則違反が起きた。
- 事実（B2-lean）:
  - Opus で USD 1.07 倍・時間 1.04 倍、成功 1 回あたり 0.50 USD（B1 0.47）。Sonnet で USD 1.20 倍・時間 1.24 倍。
  - B1 より安かった課題: Opus の P3K・P5・P8・P9、Sonnet の L1・P8、Haiku の L1・P5・P8。
- 事実（B2-best）: Sonnet 11/11、Haiku 8.7/11 で、それぞれのモデルで成功が最多（Sonnet は B1 と同数）。Opus では USD 1.44 倍で B2-lean より高い。
- 事実（使われ方）:
  - スキルの読み込みは、Opus 100%、Sonnet は B2 55% → 説明文を広げて 97%、Haiku は 15% → 42〜61%。
  - Haiku は `wikictl help` をよく読む（55〜91%）。
  - `wikictl-search` はほとんど使われなかった。
- 解釈:
  - 差の原因は、(a) 多数のファイルを 1 回で読む手段が使われないこと（主に Haiku）、(b) 呼び出しごとの fetch、(c) 履歴を読むコマンドがないこと、(d) 長いスキルを読み込む固定の費用。
  - (a)〜(c) は、まとめて読むコマンド、履歴、fetch の省略、ローカルへの書き出しで縮まった。(d) はスキルを短くし、詳細をヘルプに置くと縮まった。
  - 手順をスキルに書いても、読まれなければ効かない。モデルを問わず届くのはコマンドのヘルプ。
  - Opus と Sonnet は短いスキルで足り、Haiku は手順を具体的に書いた長いスキルのほうが成功が多かった。

### 品質と時間を加えると

費用だけで見ると Opus が最安の課題はないが、品質（成功率）と時間（成功 1 回あたりの分）を加えると、難しい課題で Opus が選択肢になる。数値は [model-cost.md](model-cost.md) の 5 節。

- 全体では、成功 1 回あたりの分は Opus 1.77、Sonnet 1.80、Haiku 3.43。Opus と Sonnet はほぼ同じで、Haiku は約 2 倍。
- Opus が最速だったのは、推論の多い P5・P6・P7。P7 では Sonnet の 0.55 倍の時間で、費用は 1.05 倍。
- Opus が単独で品質最高だったのは P4（成功率 0.75 対 0.67）。
- Haiku は、どの課題でも最速ではなく、品質でも上回らない。費用だけで選ぶ場合の候補。
- 3 軸のどれかで最良（パレートに残る）だった課題の数は、Sonnet 11、Haiku 6、Opus 4。
- 費用より時間を重視するなら、P5〜P7 のような推論の多い課題で Opus、それ以外では Sonnet を選ぶのが、この結果に沿う。

### 解釈

- 下位のモデル w が上位のモデル s より成功 1 回あたり安いのは、成功率の比 p_w / p_s が、1 回の費用の比 c_w / c_s を上回るとき。今回の費用の比は、Haiku / Opus が 0.22〜0.58（難しい課題で 0.22〜0.32）、Sonnet / Opus が 0.39〜0.96、Haiku / Sonnet が 0.33〜1.08。したがって目安は次のとおり:
  - Haiku を Opus の代わりに使ってよいのは、Haiku の成功率が Opus の約 3 割以上のとき（難しい課題）。易しい課題では約 4〜6 割以上。
  - Haiku を Sonnet の代わりに使ってよいのは、多くの課題で Haiku の成功率が Sonnet の約 5〜7 割以上のとき（P7 は約 3 割）。ただし Haiku は易しい参照（L1・L2）で入力トークンが多く、費用の比が 1 を超えたため、易しい課題でも Sonnet と同等か割高になりうる。
  - Sonnet / Opus の費用の比は 8 課題で 0.39〜0.51 で、そこでは Sonnet の成功率が Opus の 4〜5 割を下回らない限り Sonnet のほうが安い。P5・P6・P7 では比が 0.82〜0.96 と高く、Sonnet の成功率がわずかに下がるだけで逆転する。今回は Sonnet の成功率が十分高く、逆転は起きなかった。
- 逆転の主因は、トークンの増加ではなく失敗率。難しい課題では Opus も多くのトークンを使うので、入力トークンの比はかえって小さくなる（1.5〜2.0 倍）。逆転が起きたのは、Haiku の成功率が 0.17〜0.42 に落ちた P7・P8・P9（Sonnet < Haiku）と P7・P8（Opus < Haiku）。
- 難しい課題は上位のモデルのほうが結果的に安くなりうる、という見立ては Haiku に対して支持される。一方、Opus は Sonnet より安くなった課題がなく、最安の課題もなかった。
- 難しさが事前に分からないときは、全課題で成功率 0.67 以上、成功 1 回あたりの費用が最安か 2 番目だった Sonnet が、最悪の場合の費用を抑える。

### 注意

- 成功 1 回あたりの期待費用は、失敗を検知してやり直せることを前提にしている。誤答に気づけない場面では、成功率の低いモデルの費用はこれより大きくなる。
- 課題 × モデルごとに 12 回で、4 つの条件を合わせている。条件によってモデル間の関係が違う課題がある（model-cost.md の 5 節）。
- 採点を変えると結果が変わる。厳密な採点では、Opus の P3K と Sonnet の P7 の成功が下がり、Opus < Sonnet が P7 で 1 つ生じる（model-cost.md の 6 節）。P9 の並び順を問わなければ、Haiku の P9 の成功 1 回あたりの費用は Sonnet より安くなる。

## 限界

- B2-best と B2-lean は、同じ課題での探索的な試行を見て組み立てた。未知の課題での効果は、これより小さい可能性がある。
- 3 回ずつで、区間推定はしていない。Haiku の時間など、回ごとのばらつきが大きい指標がある。
- 遅延は 40 ms だけを本番で測った。遅延なしの比較はしていない。
- 同時に 3〜6 セッションを動かした。各コンテナは 2 CPU に固定したが、実時間は API の混雑の影響を受ける。
- P5 の問題文（言い換えと日本語の説明）は Opus で作り、別の呼び出しで一意に特定できることを確かめたものだけを使った。
- 題材は 3 つのリポジトリで、いずれも frontmatter が構造化された文書。構造の少ない wiki では結果が変わりうる。
- 問題文が 2 通りに読める問いが 2 つあった（P3K、P7）。ほかの課題にも曖昧さが残っている可能性がある。
- B0 の隔離は、文書の clone を渡さないことによる。イメージには wikictl と `wikictl-search` が入っており、P8-B0-sonnet-r1 の 2 回目のセッションがそれらを実行し、コンテナの中の transcript を探した（設定がないため失敗し、得点には影響しない）。
- 費用は公開の単価による換算で、サブスクリプションの利用枠の消費とは一致しない。長いコンテキストの割増し（1 回の呼び出しの入力が 200K トークンを超える場合の単価）は換算に含めていない。ただし本番の呼び出し 16,946 回に 200K を超えたものはなく（1 回あたりの入力の最大は Sonnet 112,967、Haiku 70,377、Opus 59,771 トークン）、この点による差は生じていない。

## 付録: 規則違反を許容した場合の試算

本文の「成功」は、課題文が禁じた操作をしなかったことを条件にしている。禁じた操作はシステムでは止めておらず、与えたツール（Bash と git）で実行できる。これを許容すると、点は変わらず、成功の数と成功 1 回あたりの USD が次のように変わる（ほかの行は変わらない）。

| モデル | 条件 | 成功（違反を不可） | 成功（違反を許容） | 成功 1 回あたり USD（不可 → 許容） |
|---|---|---|---|---|
| Sonnet | B2 | 10.0 | 10.3 | 0.45 → 0.44 |
| Haiku | B2 | 7.3 | 8.3 | 0.31 → 0.27 |
| Haiku | B2-lean | 6.3 | 7.7 | 0.35 → 0.29 |

- 事実: 違反のあった 12 グループのうち 8 グループは課題に正答していた。大半は P4（履歴）で、ミラーの `git log` から日付を得ていた。Opus の B2 の 3 件は `git ls-remote` を 1 回実行しただけで、P4 は 1 問を誤答しており、違反がなくても成功ではない。
- 解釈: 許容すると Haiku の B2 は B1 と同じ水準の成功（8.3 対 8.0）になる。ただしそれは wikictl を迂回して Git の履歴を使った結果で、「wikictl で足りるか」を問う本文では違反として数える。許容した値は、エージェントの環境でミラーに手が届く場合の参考値。
