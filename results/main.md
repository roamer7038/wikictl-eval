## 結論

### 1. 情報がローカルにある場合（B1・B2）と、ない場合（B0）

- 事実: B0 の点は 0.23〜0.31 で、全問正答はほぼない。B1・B2 系は Opus・Sonnet で 0.99〜1.00、Haiku で 0.83〜0.89。B0 は 2026 年に変わった値を古い値で答えた。
- 解釈: 対象の文書を読めるかどうかの差は大きく、モデルの知識では代えられない。

### 2. B2 が B1 と同等以上になるには何が要るか

- 事実（素の B2）: 点は B1 と同じ水準だが、USD は 1.2〜1.8 倍、時間は 1.7〜2.3 倍（Haiku は 2.3 倍）。時間の大半は、ファイルを 1 つずつ読む `wikictl cat` の繰り返しと、呼び出しのたびの fetch。履歴を読む手段がないため、P4 では規則に反してミラーやリモートを git で直接読むグループがあった。
- 事実（B2-lean）: Opus で USD 1.07 倍・時間 1.04 倍、成功 1 回あたり 0.53 USD（B1 0.52）。Sonnet で USD 1.20 倍・時間 1.24 倍。Opus の P3K・P5・P8・P9 と Haiku の L1・P5 では B1 より安い。
- 事実（B2-best）: Sonnet と Haiku で成功が最も多い（Sonnet 11/11、Haiku 8.7/11）。Opus では USD 1.44 倍で B2-lean より高い。
- 事実（使われ方）: スキルの読み込みは Opus 100%、Sonnet は B2 55% → 説明文を広げて 97%、Haiku は 15% → 42〜61%。Haiku は `wikictl help` をよく読む（55〜91%）。`meta`・`log`・`snapshot` は、スキルを読まなかったグループでもヘルプから見つけて使われた。`wikictl-search` はほとんど使われなかった（0〜3%）。
- 解釈:
  - 差の主な原因は、(a) 多数のファイルを 1 回で読む手段が届いていないこと、(b) 呼び出しごとの fetch、(c) 履歴を読むコマンドがないこと、(d) 長いスキルを読み込む固定の費用。
  - (a)〜(c) は wikictl の機能（まとめて frontmatter を読む、履歴、fetch の省略、ローカルへの展開）で縮まり、(d) はスキルを短くして詳細をヘルプに置くと縮まる。
  - 手順をスキルに書いても、スキルが読まれなければ効かない。モデルを問わず届くのはコマンドのヘルプ。
  - 能力の高いモデルほど短いスキルで足り、Haiku には手順を具体的に書いた長いスキルのほうが成功が多い。

## 限界

- B2-best と B2-lean は、同じ課題での試行（本番とは別の実行）を見て組み立てた。未知の課題での効果は、これより小さい可能性がある。
- 3 回ずつで、区間推定はしていない。Haiku の時間など、回ごとのばらつきが大きい指標がある。
- 遅延は 40 ms だけを本番で測った。遅延なしの比較はしていない。
- 同時に 3〜6 セッションを動かした。各コンテナは 2 CPU に固定したが、実時間は API の混雑の影響を受ける。
- P5 の問題文（言い換えと日本語の説明）は Opus で作り、別の呼び出しで一意に特定できることを確かめたものだけを使った。
- 題材は 3 つのリポジトリで、いずれも frontmatter が構造化された文書。構造の少ない wiki では結果が変わりうる。
